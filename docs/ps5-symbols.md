# What the PS5 build can name

The PlayStation 5 `eboot.bin` is a plaintext Prospero image inside a SELF
container, 195,555,354 bytes with 150 MB of it text. It is the second witness
for the RPF9 layer (`docs/ps5-build.md`, `docs/rpf-crypto.md`), and this page is
about a different question: how much of the *symbolic* information a decompiler
needs it actually keeps.

Short answer: it keeps the system-library manifest, the AGC and shader toolkit
names, and the libc error strings in the game's own `sce_module/libc.prx`. It
does **not** keep RAGE source paths, asserts, mangled names, RTTI, or any
NID-to-name table. The firmware tree names the modules that implement each
library but ships every one of them encrypted, so it cannot name the calls.

## The address correction

The first pass over this image read the ELF `p_offset` values as file offsets.
They are not: a SELF repacks each segment into its own block, listed in the entry
table after the 0x20-byte header. For text that means the bytes start at
`0x485d0`, not `0x4000`, and every address in the earlier notes was `0x445d0`
too high.

Three independent measurements:

| Check | Result |
|---|---|
| bytes `0x4000..0x485d0` | 280,016 bytes, **all zero** |
| text block start | `cc` padding, then a function prologue at block + `0x10` — where `_start` belongs |
| `e_entry` `0x4366790` | a function entry with `push rbp; mov rsp,rbp; push r15/r14/rbx` only at file `0x43aed60` = `e_entry + 0x485d0` |

The deltas are per-segment, so no single `VA - 0x4000` rule works, and a
cross-segment reference also shifts by the difference between two deltas:

| Segment | `p_offset` | SELF block | delta |
|---|---|---|---|
| text | `0x00004000` | `0x000485d0` | `+0x445d0` |
| rodata | `0x08f70000` | `0x08fb93b0` | `+0x493b0` |
| data | `0x09ed0000` | `0x09f18b90` | `+0x48b90` |
| data | `0x0a3f4000` | `0x0a43e4f0` | `+0x4a4f0` |
| `---` | `0x0abe54f0` | `0x0ac33c10` | `+0x4e720` |

What this does and does not change: the *bytes* a window used to include were
the right ones for the RPF bodies, because the literal and the code moved
together inside text, so `fiPackfile::Open`, `fiFile::Open`,
`fiFile::Initialise` and the device selector are the same functions as before —
they just carry corrected labels now (`0x8e0990`, `0x2844e50`, `0x2844f70`,
`0x8e1100`). Re-decompiling `0x8e0990` under the corrected window reproduces the
recorded body field for field, including the `0x52504639` compare and the
`+0x1A/+0x1C/+0x20/+0x22/+0x24/+0x2C/+0x2D` reads behind
`fiPack_ComputeLayout`.

```sh
python3 tools/ps5elf.py info 6RE/DUMPS/PS5Dump/eboot/eboot.bin   # prints both offsets
python3 tools/ps5elf.py va  6RE/DUMPS/PS5Dump/eboot/eboot.bin 0x929092   # -> 0x8e0ac2
python3 tools/ps5elf.py off 6RE/DUMPS/PS5Dump/eboot/eboot.bin 0x8e0ac2   # -> 0x929092
```

`convert` uses the block offsets, so windows and `--entry` are image addresses.

## The import manifest

The only symbolic information a stripped Prospero executable keeps on purpose is
the set of system libraries it imports. `tools/ps5imports.py` recovers it from
the loader table — `libSceX.prx\0libSceX\0` pairs in the last load segment — and
resolves each library to the firmware module that implements it:

| Library | Firmware module | Module state |
|---|---|---|
| `libSceAgc` | `system/common/lib/libSceAgc.sprx` | encrypted |
| `libSceAgcDriver` | `system/common/lib/libSceAgcDriver.sprx` | encrypted |
| `libSceAcm`, `libSceAjm`, `libSceAudioOut`, `libSceAudioOut2` | same names under `common/lib` | encrypted |
| `libScePad`, `libSceMouse`, `libSceIme`, `libSceImeDialog` | same names | encrypted |
| `libSceNet`, `libSceNetCtl`, `libSceHttp`, `libSceSsl`, `libSceNpAuth`, … | same names | encrypted |
| `libSceSaveDataDialog`, `libScePlayGo`, `libSceShare`, `libSceRazorCpu`, … | same names | encrypted |
| `libSceNpCppWebApi` | `eboot/sce_module/libSceNpCppWebApi.prx` | **plaintext** |

46 libraries, 45 resolved, 1 plaintext (`libSceNpCppWebApi`, shipped with the
game), 0 unresolved. `libSceShare` resolves through its `.native` module.

The manifest is real evidence for *what* the game uses: AGC and AGC driver means
graphics go through the PS5 API rather than GDK, `libSceAjm`/`libSceAcm` mean
hardware audio decode, `libSceRazorCpu` is the profiling hook. It is not a
function-name table: the loader looks functions up by NID, and no NID-to-name
list exists in this image or in anything decrypted in the dump.

Generated by:

```sh
python3 tools/ps5imports.py \
    --eboot 6RE/DUMPS/PS5Dump/eboot/eboot.bin \
    --firmware PS5FW/dumps/11.60/extracted
# imports/ps5_libraries.tsv   library, prx, name offset, vaddr, module, state
# imports/ps5_firmware.tsv    every module in the tree and its container
```

## What the strings are worth

Measured on the eboot:

| Measure | Count |
|---|---|
| strings of 6+ characters | 237,321 |
| C++ qualified names (`::`) | 275 |
| `Agc::Toolkit::…` | 62 |
| mangled `_Z…` | 13 |
| `typeinfo for` / `vtable for` | 0 |
| `../…cpp` source paths | 0 |
| assert-like strings | 22 |
| `packfile` anywhere | 0 |

So the hope that a bigger image is a less-stripped one does not hold here: the
RAGE file layer carries no assert or path literal at all, which is why Xbox and
PS5 agree that the object graph has to be read out of code, not out of strings.
What the image does name is the graphics side — `Agc::Toolkit::cs_copytexture3d_s2f_c`,
`Agc::Toolkit::pix_clear_sint16_abgr_p`, `psr_qbvh_*` shader program names — and
asset-facing tokens (`AUD_PED_HUMAN`, `alphaVehicleLodG`, `ped.detail%s[%d].roughness`)
that are shared with the Xbox build. Those are useful for identifying graphics
and audio code, not for naming the archive layer.

The one RPF-related literal is still `%s.rpf`, with no code reference, exactly as
on Xbox.

## The firmware tree

`PS5FW/dumps/{11.60,12.70}/extracted` holds 3.4 GB per version and 588 modules
across `system/`, `system_ex/`, `app/`, plus the raw flash images. Every
`.sprx`/`.prx`/`.elf` in it starts with SELF magic `5414f5ee` — an encrypted
body: 588 encrypted, 0 readable. That is a container fact, not an analysis
guess, and it is why the tree cannot name the eboot's imported functions.

Two modules are readable because they ship with the game:

* `eboot/sce_module/libSceNpCppWebApi.prx` — plaintext SELF (`4f153d1d`), 7.9 MB.
* `eboot/sce_module/libc.prx` — plaintext SELF, 1.9 MB, 7,253 strings of 6+
  characters and 171 libc message strings (`memcpy_s: buffer overlap`,
  `[%s] Please use SCE_LIBC_INIT_MALLOC_MANAGED_SIZE() before malloc_stats().`).
  No `sce*` export names survive, so functions are identifiable by their
  messages, not by name.

`2_updatemode.elf` in either firmware version is also encrypted, so the
"decrypted firmware" does not exist in this dump; see the blocked-firmware note
in `docs/ps5-build.md`.

## Importing the types and classes into Ghidra

The Xbox project gets its vocabulary from GDK import tables and GTA V's class
list. A PS5 build has no GDK, so the equivalent is built from the PS5 evidence
plus this tree's own recovered headers:

```sh
python3 tools/make_ps5_types.py        # names/rage_structs.tsv
# then, in the gta6_full project with the eboot open:
#   ApplyPs5.java  <projectRoot>
```

`make_ps5_types.py` parses a deliberately small C subset from
`packfile_crypt.h`, `packfile.cpp` and `rage_types.h` and refuses anything it
cannot account for byte-for-byte: 7 structures, 43 fields, with every
`static_assert` in the source cross-checked. `fiPackHeader9` comes through
complete (`magic` `+0x00` … `reserved` `+0x34`, size `0x40`), as do
`fiPackIndex`, `fiPackLayout`, `fiPackRun` and the vector primitives;
`fiFile`, `fiPackfile`, `fiPackBlock`, `fiMountTable`, `atString`, `fiDevice`,
`fiPackCrypt`, `Matrix34/44` and `Vector3` are skipped because they contain a
member of unknown width (an `atString`, a `rest[0x80 - 0x70]` expression, a
template).

`ApplyPs5.java` then:

* creates one Ghidra external library per entry in `imports/ps5_libraries.tsv`
  and labels each loader-table name string (`libSceAgc_name`), so the table is
  readable in the listing;
* builds the RAGE structures under `/rage` with real field names and padding, so
  the decompiler prints `header->entryCount` instead of `*(uint *)(param_1 + 0x24)`;
* registers all GTA V classes as opaque types under `/gtav/<namespace>` from the
  same `names/gtav_classes.tsv` that `ApplyRefs.java` uses on Xbox;
* applies `matches/ps5_string_names.tsv` if present (`va<TAB>name`), and renames
  nothing else.

It prints the same `REFS|…` summary line as `ApplyRefs.java`, so `tools/progress.py`
reads either build. The script compiles against Ghidra 12.1.4
(`javac -cp $(find /home/nate/ghidra -name '*.jar' | tr '\n' ':') tools/ApplyPs5.java`).

## Still unknown

* ~~**NID to name.**~~ **Solved by generation.** No table ships the mapping, but
  a NID is `f(symbol)` — `sha1(symbol + salt)` folded into 11 characters — so
  names are produced by encoding SDK symbols and joining on equality, not by
  searching for a table. `tools/ps5nids.py` does this; see the section below.
  Import stubs can now be named wherever the SDK declares the symbol.
* **Decrypted system modules.** Every firmware module is encrypted; the module
  manifest is all that tree contributes.
* **RPF9 TOC contents.** Unchanged from Xbox: no key constant in either image,
  and the PS5 build reaches AES through AES-NI rather than the RAGE tables.

## NID = sha1(symbol + salt)

An 11-character NID is a *hash of the symbol name*, not an opaque id:

```
digest = sha1(name + 518d64a635ded8c1e6b039b1c3e55230)   # 16-byte salt
digest[0:8] = digest[0:8] byte-swapped
digest[8:16] = 0
take three 24-bit groups -> 11 chars of
"ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+-"
```

So the direction that matters is **name → NID**, and a NID is named by encoding
the candidate symbols and looking for a match. `tools/ps5nids.py` implements it
and is byte-identical to `/opt/ps5-payload-sdk/bin/prospero-nid`.

### Verification

Encoded names are checked against the AnyDevKit NID map
(`ps5ref/AnyDevKit/3rdparty/ps5-nid-map/data/Modules/*.inc`, 546 modules):

```
$ python3 tools/ps5nids.py verify
sceKernelGetProcessTime                  4J2sUJmuHZQ  in NID map
sceSystemServiceGetStatus                rPo6tV8D9bM  in NID map
sceSaveDataMount                         32HQAQdwM2o  in NID map
3/3 symbols found in the AnyDevKit NID map
```

That is a real join, not a self-test: the `.inc` files were written by a
different tool from the salt alone.

### The shipped database (better than generating)

GhidraProspero — the PS5 loader extension installed in Ghidra here — ships a
`DynlibDatabase` of **154,478** NID→symbol pairs, including libc, libkernel,
SCE C++ and inspector symbols:

```
~/.config/ghidra/ghidra_12.1.4_PUBLIC/Extensions/GhidraProspero/data/nid_db.xml
  <Entry obf="f7uOxY9mM1U" sym="__stack_chk_guard"/>
```

`tools/ps5nids.py lookup` reads it automatically (it resolves `f7uOxY9mM1U` to
`__stack_chk_guard`, `2sWzhYqFH4E` to `_Stdout`, `4J2sUJmuHZQ` to
`sceKernelGetProcessTime`, all three confirmed by the loader at analysis time).
`export-db` writes it as a TSV; the 16 MB file is generated, not committed
(`names/ps5_nid_db.tsv` is ignored). So the order of preference is:

1. the shipped database, when GhidraProspero is installed;
2. the generated SDK-header table, for symbols the database names differently
   or not at all;
3. nothing — an unresolved NID stays a number.

GhidraProspero's own `NIDAnalyzer` also runs during `analyzeHeadless` and
resolves the eboot's stubs in place, which is where the three names above were
first observed.

### The ps5-nid-map corpus

`ps5ref/AnyDevKit/3rdparty/ps5-nid-map/data/Modules/*.inc` is the third source
and the largest:

* **541** module files, **777** `PS5_NID_MAP_LIBRARY` blocks, **328,561** NIDs,
  each `"NID"` string inside the library block it belongs to;
* it is the only source here that also names the *module* for a NID, e.g.
  `libSceAgc`, `libScePsml_mfsr2` — the two modules that carry the 17 stubs the
  GhidraProspero database does not have.

`tools/ps5nids.py` reads it automatically (`--nid-map` overrides the path).

### The eboot's imports, named in bulk

`tools/DumpImports.java` prints every external/thunk function of the analysed
program, and `tools/ps5nids.py imports --log <analyzeHeadless log>` joins those
NIDs against the three sources:

```
wrote names/ps5_eboot_imports.tsv: 730 stubs, 713 named, 17 module-only, 0 unknown
```

| source | stubs | gives |
| --- | --- | --- |
| GhidraProspero `nid_db.xml` | 713 | symbol |
| `ps5-nid-map` corpus | 17 | module only (that corpus lists NIDs, not names) |
| SDK headers | 0 | — |

`tools/ApplyImports.java` then renames those stubs in the project itself:
`IMPORTS_APPLIED|730|skipped=0`, and a second run reports 706 of them
`already named`, so the renames persist.

The file is `va`, `nid`, `library`, `symbol`, `source`, so a stub address in the
image maps straight to the symbol the loader would bind.

### The generated table

```sh
python3 tools/ps5nids.py scan \
  --sdk ../SonySDKS/PS5/11.000/target/include \
  --sdk /opt/ps5-payload-sdk/target/include \
  --out names/ps5_nid_symbols.tsv
# wrote names/ps5_nid_symbols.tsv: 3407 symbols from 2 header roots
```

`names/ps5_nid_symbols.tsv` is `nid`, `symbol`, `source` (3,407 rows, tracked
because it is small and reproducible). Look up either way:

```sh
python3 tools/ps5nids.py encode sceSaveDataMount
python3 tools/ps5nids.py lookup 4J2sUJmuHZQ
```

Sources scanned:

| Tree | Role |
|---|---|
| `SonySDKS/PS5/11.000/target/include` | Sony's own 11.000 headers, 987 files — the authoritative names and signatures |
| `/opt/ps5-payload-sdk/target/include` | payload SDK, 2,598 files, broader libc/kernel coverage |
| `ps5ref/AnyDevKit/3rdparty/{AnyPS5,ps5-nid-map}` | NID lists per module; used to **verify** the encoder, not to name |
| `ps5ref/KytyPS5/src/loader` | symbol database + runtime linker, shows how a loader consumes NIDs |
| `ps5ref/ps5-tools/{self-tools,backport,orphan-scan}` | `resolve_call.py`, `fw_exports.py` — NID joins by library/module |

### Limits

* A NID absent from the table means "not declared by these headers", never "not
a PS5 import". Aliases are a real gap: 11.000 declares `sceSaveDataMount3` and
the plain `sceSaveDataMount` exists only as a macro in older SDKs.
* The join names *imports*. A statically linked internal function has no NID.
* Neither SDK contains the game's own symbols, so this cannot name a `sub_...`
body — only the system calls its imports target.
