# Matching toolchains: what we can use and what we cannot

Four matching projects were read before choosing the progress story:
`isle` (a complete decompilation that uses reccmp and reprobit),
`reccmp`, `reprobit`, `objdiff`, plus `cinnabar` for the GDK-to-Rust angle.
This note records what each one can actually do for a **retail PE32+ x64 MSVC**
target, because two of the four turn out to be unusable and saying so is more
useful than wiring them up anyway.

## Summary

| Tool | Supports | Fits GTA VI? | Use |
|---|---|---|---|
| `objdiff` | x86_64, MSVC demangling | **yes**, arch-wise | progress reporting + per-function diff, once objects exist |
| `reccmp` | 32-bit x86, MSVC ~4.2 | no | annotation syntax only |
| `reprobit` | MSVC 4.2 / 5.0 profiles | no | the *idea* of a certified rebuild, as objective 7 |
| `isle` | 32-bit x86, MSVC 4.2 | no, but its progress graph is the model | `docs/progress.svg` |
| `cinnabar` | Rust, GDK client | no direct reuse | GDK/NetherNet behaviour reference only |

## objdiff — usable, and the reason objective 7 is last

objdiff compares two **relocatable object files** (`.o` / `.obj`). It supports
x86_64 and demangles MSVC symbols, so nothing about this target is out of scope
for the tool. What is missing is the input: `game_scarlett_master.exe` is a
linked image, and no per-translation-unit `.obj` for the retail build exists in
the DUMP. There is nothing to diff against yet.

`tools/gen_objdiff.py` therefore writes the real `objdiff.json` — every function
folder in `src/` becomes a unit with `target_path` and `base_path` pointing at
`build/<area>/<Function>.obj`, and `status: awaiting_build`. When a unit can be
compiled with a matching-toolchain `clang-cl`/`MSVC` x64 invocation, objdiff
can load the project and diff it without any further wiring.

The README embeds `docs/objdiff.svg`, generated by `tools/progress.py` from
`docs/progress.json`, so the matched-code bar is a computed number, not a
hand-typed claim. It reads 0 today.

## reccmp — not usable as a matcher, usable as a convention

`reccmp` matches recompiled functions against the original by source comment:

```cpp
// FUNCTION: LEGO1 0x100b12c0
MxObject::MxObject()
```

Its own README states the supported target: "C++ compiled to 32-bit x86 with old
versions of MSVC (like 4.20)". GTA VI is x64 MSVC 19xx, which is outside that
range, so reccmp's diff engine cannot be pointed at this binary. The *annotation
convention* is still good and this project already carries the equivalent:
every body has `// Address:` and `// Name:` in its header, written by
`tools/ReSource.java` and readable by `tools/reindex.py`. No reccmp install is
needed to keep that property.

## reprobit — not usable, but it names objective 7 correctly

ReproBit rebuilds a binary byte-for-byte with the original compiler and proves
three separate claims (identical bytes, adjustments preserve logic, the build
really came from the declared source). Its supported profiles are MSVC 4.2 and
5.0. Ours would need an MSVC 19xx profile that does not exist in the tool, plus
the retail `.lib`/`.obj` files, which are not in the DUMP.

The reason it is documented anyway: it is the correct definition of
"byte matching" for objective 7. Matching means *the rebuilt object equals the
retail object and the equivalence is demonstrated*, not "the disassembly looks
similar". That standard is what `docs/objectives.md` objective 7 refers to.

## isle — the progress-graph model

isle publishes a generated SVG per binary (`ISLEPROGRESS.SVG`,
`LEGO1PROGRESS.SVG`) plus a reccmp accuracy report and a ReproBit verification
report, all embedded in one README. This project copies the *reporting shape*
exactly, because it is the one part that transfers without the toolchain:

* `docs/progress.svg` — ring per binary, filled by measured coverage, with the
  counts printed beside it (isle's graph, our denominator).
* `docs/objdiff.svg` — the matched-code bar a decomp.dev/objdiff project shows.

Both are generated by `tools/progress.py` and both appear in the same README
section, which is what "make them both exist" means here.

The one thing that does **not** transfer is isle's denominator. isle knows how
many functions the retail binaries contain because it has the source to compare
against. This image has 299,257 `.pdata` function starts and no source, so the
ring can only measure *bodies written out of those starts*. It is labelled that
way in the SVG itself so the graph cannot be misread as an accuracy figure.

## cinnabar — reference, not code

`cinnabar` is a from-scratch Rust client for Minecraft: Bedrock, not a GDK port
of one: the tree is `cinnabar` (Rust/Bevy/wgpu) talking over a local socket to
`bedrock-core` (Go), with RakNet and NetherNet transports and an
`xboxpresence` package. There is no GDK call layer to lift into this project.

Two things are still worth reading from it when the network objectives come up:
the `core/xboxpresence` package (how a non-Microsoft client presents an Xbox
identity) and `docs/profile-parity.md`, which is the only place in the tree that
discusses GDK behaviour. Neither helps decompile `game_scarlett_master.exe`.

## What this leaves

* **Naming**: string evidence + GTA V source directory, as before
  (`docs/source-layout.md`).
* **Structure discovery**: constant scanning (`tools/anchors.py`), which is what
  found the `RPF9` magic and the two archive functions.
* **Progress**: generated SVG, two reports, one README.
* **Correctness**: objdiff on rebuilt objects, objective 7, currently 0.
